# EPIC N conformance matrix: encrypted retained copies and recoverable key custody

What this file is for, and what it is not. It is not a summary of the work: it is the list of claims EPIC N makes, each one tied to the test that will go red if the claim stops being true, plus the **mutation that has to be run and watched to fail** before the row may say `PASS`. `BLOCKED` is for a claim whose proof has not landed on `main`, with the sub-issue that unblocks it in the status cell and in the last column. Nothing here is green because nobody looked.

**Every row is `BLOCKED` on the day this file lands, and that is the point.** Nothing of this epic exists in the tree yet, so no row can cite a proof of its own. Where a row names a test, it is an existing test the proof will extend or stand beside, never one I made up; the issue that commissioned this file forbids naming a test or gate that does not exist, and the guard that reads this file resolves every backticked path a `PASS` row cites. A row that went green in the same pull request that wrote it would be the failure this file exists to prevent, so no row flips until the pull request that lands its proof on `main` has also had its falsification run and watched to fail.

`docs/EPIC-N-encrypted-retained-copies.md` is the contract. Its phase exit gates are the checkbox lists this file numbers `N1.n` and `N2.n`, in order, one row per line. Its section 3.6 consensus table is `NC-01` to `NC-19`. Its section 6 guard table is the `NV.n` ledger, one row per guard, in order, with the ten key-material surfaces as ten rows and not one.

## Reading a row

| Column | Means |
|---|---|
| ID | `N1.n` and `N2.n` for exit-gate lines, `NC-nn` for the adversarial-review findings, `NV.n` for the planted-violation ledger |
| Claim | What is asserted, in the epic's words |
| Executable proof | What exists today that the proof will extend, as `<package dir>:<TestName>` for a Go test in that directory or a bare path for a file. Nothing here names a test that is not in the tree. The row says in words what the new proof has to be |
| Falsification | The mutation that must turn the proof red. Once run, the row gains the date and what caught it |
| Status | `BLOCKED (#issue)` now, naming the sub-issue that unblocks it. `PASS` only once the falsification has been run and watched to fail, with the date. `PARTIAL` when a half cannot be shown from here, saying what is missing. `BY HAND` for a check nobody can automate, naming who checked what and when |
| Waits on | The sub-issue, and the pull request once one is open, that has to land first |

## The guards that read this file

`docs/epic-checklist.md` section 1 calls this the item that matters most, and it is gated from the day it lands. `core/tests/compat/matrix_test.go` carries a table of (specification, matrix) pairs and this pair is in it, so five tests hold this file to the specification on every run of the gate: one row per exit-gate line in each phase, numbered contiguously (`TestTheMatrixHasARowPerGateLine`); one `NV.n` row per guard in the specification's section 6 table, numbered contiguously (`TestTheViolationLedgerIsHeldToTheSpecsGuardTable`); every path a `PASS` row cites resolves and a `PASS` row that cites nothing is refused (`TestTheMatrixDoesNotCiteSuitesThatDoNotExist`); a specification checkbox is ticked exactly when its row is `PASS` (`TestTheSpecsExitGateBoxesAgreeWithTheMatrix`); and every `BLOCKED` row cites an issue that GitHub says is still open (`TestEveryBlockedRowCitesAnIssueThatIsStillOpen`, with `TestTheBlockedCitationGuardCanFail` as its offline mutation self-test). The registration was committed red, before these two documents existed.

What that guard does not yet hold, and #998 adds in a checker of its own in the shape of `core/tests/assurancegate/matrix_test.go`: a `PASS` row has to cite a mutation that occurs in a self-test and the date it ran, a `BY HAND` row has to name a person and a date, a `PARTIAL` row has to say what is missing, and at the end no row may be `BLOCKED`. Until then those rules are read by a person, which is why every row below already carries a falsification written so that checker can read it.

## The limits of this matrix

Stated plainly, because a table of `BLOCKED` cells will one day be a table of `PASS` cells and invite the reader to assume the rest.

- **An encrypted copy is not a recovered one.** The stored-bytes digest says the ciphertext at the key is the ciphertext that was uploaded. Only a decrypt-verify says the plaintext is the artifact, and only EPIC Q's recovery test says the operator's validator accepts it. Three claims stay three.
- **Object names stay visible.** Nothing here hides the source, set or artifact name from whoever holds the bucket. That is a documented limitation with a reason (NC-10), and no row claims otherwise.
- **The DR bundle is the only thing that changes the threat model.** A managed key on the same host as the copies protects against a bucket holder, not against someone who can read the state directory. The custody rows prove the file mode, not the threat model.
- **Nothing here designs cryptography.** The format rows prove that the chosen library is the one used and that its failure modes fail closed here. They do not audit the library.
- **A real NAS or a real provider.** Memory and timing numbers will be measured on one host, named in the row. No eleven-provider fleet and no real off-site bucket at scale are claimed.
- **The captures are not a store screenshot.** `docs/submission/screenshots.md` needs real hardware, a real installation and a real SFTP source, and a mock must never be substituted there.

## The ungated reverse sweep, by hand (N1.16)

Nothing in the tree catches a command that has no way to be done in the browser, so I swept it by hand for N2.4 (#997) and I am recording it here instead of letting it read as a green row. I checked on 2026-11-09, at the tip of `feat/995-web-ui` (`2ccf8595`), by reading `core/cmd/retnd/encryption.go` and `core/cmd/retnd/main.go` against `ui/shared/src/encryption/` and the pages that mount it. I ran nothing, so this is a reading and not a test.

Every route under `/api/v1/encryption` (and the per-set `PUT`/`DELETE`) has a browser control, and the control echoes the verb (`ui/shared/src/encryption/encryptionCommands.ts` holds the table). What the terminal can do that the browser cannot:

- **`encryption provider test --managed-key ID`.** The browser tests a declared external reference and has no control for probing a managed key. The route accepts both; the screen draws one.
- **`encryption key confirm <id> --digest D`.** The browser confirms the newest export of a key and never asks for the digest, so confirming a specific, older export is terminal-only.
- **What `catalog rebuild` says about encrypted copies.** The rebuild names, per encrypted copy, the key it needs and whether this deployment knows it. I found no screen that renders that finding.
- **`--json`.** Output formatting, not a capability.

Not a gap, listed so nobody re-checks it: `key export --out FILE` and the browser's Download bundle are the same operation with a file and a download as their two ends.

I have not changed the `N1.16` row's status for this. Its other halves (the route, gap-sentence and `reference.html` guards) belong to the test run, and a row that says `BY HAND` still wants a name and a date in its own cell when the matrix is closed out (#998).
