# EPIC R conformance matrix

Every gate line declares, as a cell: what it certifies, where it is asserted, and
the planted violation that has to make it red. One row per line of the spec's two
exit gates, one per planted violation the spec names that no gate line already
carries, with nothing dropped for not being ready yet.

`docs/EPIC-R-rename-backupd-to-retnd.md` is the contract. This file is the account
of which parts of it are checked by something that has been watched to fail, which
parts are checked by nothing, and which issue owns each gap.

## Why this file exists in this shape

A rename is the change most likely to produce a matrix that is entirely green and
entirely worthless, because the obvious check — "does the old name still appear?" —
passes trivially the moment somebody runs search and replace, and says nothing
about whether the product still works. Three checks in this repository were found
in a single day that could not fail, and this epic adds a guard whose naive form
has **fifty** false positives on the tree it ships with (`BackupDetailPage`,
`BackupDefaultsPage`, `BackupDomainPolicy` and six more). A guard that noisy gets
deleted, and a matrix that certifies it is worse than no matrix.

So every row carries a **falsification**: the specific mutation that must turn
that cell red. A row whose falsification has been run and watched fail is `PASS`.
A row whose falsification cannot be run yet, because the code it would mutate does
not exist, is `BLOCKED`, with the issue that unblocks it. There is no third
reading, and in particular there is no row that is green because nobody looked.

Three rows carry a **positive control** as well as a falsification, and they are the
three that matter most. R1.1's control is a file containing every lookalike the guard
must not catch: without it, "the guard is green" is indistinguishable from "the
guard matches nothing". R1.9's control is that a genuinely fresh install still
first-runs: without it, "it adopted the legacy path" is indistinguishable from a
product that can no longer be installed. R2.17's control is a deliberately failing
check being *blocked* by branch protection on the freshly transferred repository:
without it, "branch protection restored" is a tick nobody can tell from a lie,
because a required-check list is silently empty on a new repository.

Two rows, R2.4 and R2.14, can never be better than `PARTIAL` once their work lands,
and that is the honest outcome rather than a gap waiting to close. R2.14's art half
has landed (#893) and the row is `PARTIAL` now. R2.4's store screenshots need real hardware, a real
installation and a real SFTP source, and §10 of the checklist forbids substituting a
mock for any of them. R2.14's subject is artwork: no text guard can read text that
has become an SVG `<path>` or read a raster at all — the guard's own `-I` flag
guarantees the second. So that row automates what can be automated (a manifest held
to the filesystem, a string scan of SVG `<text>`/`<title>`/`<desc>`) and names a
human acceptance step for the rest. Calling a human step `PASS` is how "unverified"
becomes "certified".

## How to read an outcome

| Outcome | Means |
| --- | --- |
| `PASS` | The check exists, runs in `scripts/ci-local.sh`, and has been shown to go red against a real planted violation. The falsification column names the mutation and it is automated in `scripts/rename/selftest.sh` or `scripts/compat/selftest.sh`. |
| `PARTIAL` | Part of the claim is checked and shown to fire, and the rest is not: either it waits on an unlanded issue, or it cannot be run here at all. The row says which half is which and which of those two it is. |
| `BLOCKED` | The check is specified here and cannot conclude today, because the code it certifies is not merged. Not a pass, and not a fail. The row names the issue. |

`BLOCKED` is a declaration, and it is checked rather than trusted. The four
structural tests in `core/tests/compat/matrix_test.go` were bound to a single
hard-coded pair of paths — `docs/EPIC-E-alternative-storage.md` and
`docs/conformance/epic-e-matrix.md` — so nothing checked *this* file at all;
#887 replaced those two constants with a table of (spec, matrix) pairs and added
this one, and the tests now run as a subtest per pair. Each of them is watched to
fail against this file specifically, not only against EPIC E's: the landing PR
plants a row citing a path that does not exist, a `BLOCKED` row citing a closed
issue, a ticked spec checkbox whose row is not `PASS`, and a dropped row, against
a copy of this file, and records each red.

What they hold: `TestTheMatrixDoesNotCiteSuitesThatDoNotExist` fails if a `PASS`
or `PARTIAL` row cites a path the repository does not have, and
`TestEveryBlockedRowCitesAnIssueThatIsStillOpen` resolves every issue a `BLOCKED`
row names against GitHub. `TestTheMatrixHasARowPerGateLine` compares the row ids
against the spec's own exit-gate checkbox lists, and
`TestTheSpecsExitGateBoxesAgreeWithTheMatrix` holds those checkboxes to these
outcomes in both directions, so a box cannot be ticked by hand and a row cannot be
dropped to tidy the table. `TestTheViolationLedgerIsHeldToTheSpecsGuardTable`
counts the `V.n` rows against §4 of the spec: this ledger carries only the guards
no gate row above already covers, so it is held to being contiguous from 1 and
never longer than the spec's own guard table, rather than to EPIC E's stricter
one-row-per-guard promise.

Two numbers that guard against a silently empty parser: this file's ids are
`R1.n`, `R2.n` and `V.n`, and EPIC E's are `P1.n`, `P2.n` and `Vn`, so a regexp
written for one matches nothing in the other and would read exactly as clean. The
tests fail on a zero-row parse for that reason.

As of #895 (R2.5), the last child of this EPIC's in-tree half, the counts are
13 `PASS`, 8 `PARTIAL` and 7 `BLOCKED`. Every one of the seven is blocked on the
same thing: FR-41's **organisation cutover**, which creates the `retnd`
organisation, transfers both repositories, re-issues the cosign identity, moves
the GHCR package and the Pages origin and restores branch protection. None of
that is in a diff and none of it was in #895's in-tree half, which is why those
rows still cite #895 and why #895 does not close with them.

Two of the seven deserve naming here rather than being read off the table,
because a reader could mistake them for bookkeeping. R2.1 wants an EMPTY
`pending` list and #895 drained it from sixty tokens to three -- `backupd`,
`Backupd`, `backupdproject` -- which are the tokens the coordinates spell. But
those three also still match about 2,360 occurrences that are not coordinates
and that no issue in this EPIC owns: code comments naming the retired CLI,
host-side NAS directory names section 6 of the spec deliberately cut, the tests
and compat cells that exercise the aliased shims, and four container labels
`core/internal/hostrunner` still sets under the old prefix. So R2.1 and R2.11
need the cutover AND a sweep nobody has scoped, and the guard's own `pending`
comment enumerates the four groups with their measured sizes rather than
leaving a reader of three tokens to infer a small job.
