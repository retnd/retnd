# EPIC V conformance matrix

Specification: `docs/EPIC-V-encryption-residue.md` (FR-105 through FR-107). Designs: `docs/design/EPIC-V-detailed-designs.md` (#1526); its appendix is what this file's rows were rewritten to on 2026-11-19.
Tracker: #1512. Sub-issues: V1.1 #1513, V1.2 #1514, V1.3 #1515, V2.1 #1516, V2.2 #1517. This file lands under #1511. Measured on `origin/main` at `37711f3c`.

One row per exit-gate line of the specification's section 7 and per planted violation of its section 8. Every row carries a **falsification**: the mutation that must turn that cell red. A row is `PASS` only once that mutation has been run and watched to fail. A check that passes on the tree it ships with has proven nothing (`docs/epic-checklist.md` section 12).

## Why this file is short

EPIC V is mostly a record of what I decided not to build. Five of EPIC N's seven cut items are rejected, so most of the rows below are guards that hold a rejection in place (V-02, V-06 to V-09), and the rest certify the two things that survive: an external key can be superseded, drained and retired without stranding its copies, and the backlog after a rotation can be read and cleared. A rejected item has a row only where a test can fail if it comes back. Where an existing control already plants the violation, the row cites it by its label in `scripts/bdtools/encryption/controls_n_a.py` or `controls_n_b.py` instead of writing it again; new controls go in `controls_v.py`.

## How to read an outcome

| Outcome | Means |
| --- | --- |
| `PASS` | The check exists, runs in `scripts/ci-local.sh`, and has been shown to go red against a real planted violation. |
| `PARTIAL` | Part of the claim is checked and shown to fire, and the rest waits on an unlanded issue or cannot be run here. The row says which. |
| `BLOCKED` | The check is specified here and cannot conclude today because the code it certifies is not merged. Not a pass and not a fail. The row names the issue. |
| `BY HAND` | There is no automated check and there will not be one, because the question is about a person reading a screen or a page. The row says who checked, against what, and when. |

Every row below is `BLOCKED` today, all 27 of them. V-15 (a backlog metric) was removed when the metric was cut on 2026-11-19, and its number is not reused so that nothing citing V-16 onwards moves. This file lands with the specification, before any implementation, which is the only state in which "no row is green because nobody looked" is verifiable by inspection.

## How the closing check enforces it

The exit gate's "no `BLOCKED` row" line is a mechanism, not a reading. `scripts/release/check-epic-v-closed.sh` calls a matrix checker in closing mode, which parses this file's tables and exits non-zero, naming the row id and its issue, for every row whose outcome cell begins with `BLOCKED`. Its self-test, `scripts/tests/epic-v-closure.test.sh`, plants a `BLOCKED` row in a throwaway copy and requires the check to name it, with this file as it stands at close as the control. Until those exist, row V-28 is the only place the rule lives, and it is `BLOCKED` with it. Registering this pair in `core/tests/compat/matrix_test.go` needs `V1.n` gate ids, `VV.n` ledger ids and a `### Phase 1 exit gate` heading, a reshaping V2.2 does in the same pull request, as EPIC O defers its own.

## Rows this epic deliberately does not have

Naming them is part of the matrix: a reader should be able to tell an absent row from an overlooked one.

- **No KMS or Vault provider row, no second-cipher row, no object-name row, no compression feature row, no scheduled decrypt-verify row, no key-usage audit row.** Each was a cut item of EPIC N and each is rejected in the specification's section 3. Where a test can fail if the rejected thing appears, the row is a guard (V-02, V-06, V-07, V-08, V-09); where nothing can fail because nothing is built (the audit surface), there is no row.
- **No decrypting `recover` row.** Rejected in the specification's section 2.
- **No settings or migration row of its own.** The one config key is V1.2's and is held by V-12 (it works) and V-25 (it is the only fixture pair and no migration came with it).
- **No backlog metric or health row.** Both were cut on 2026-11-19 (no reader); V-15 was the metric's row and is gone.
- **No row for re-encrypting an artifact that still has a local copy.** That is #1545, outside this epic; V-26 checks the docs say so.
- **No capability-contract or provider row beyond V-24.** Nothing here is platform behaviour.
- **No store-submission row.** No listed screen changes; V-26 records that judgement, and had one changed, `docs/conformance/submission-preflight.md` would have a row going back to outstanding.
