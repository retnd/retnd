# EPIC Q conformance matrix: artifact recovery, scheduled scrubbing and recoverability assurance

What this file is for, and what it is not. It is not a summary of the work: it is the list of claims EPIC Q makes, each one tied to the test that will go red if the claim stops being true, plus the **mutation that has to be run and watched to fail** before the row may say `PASS`. `BLOCKED` is for a claim whose proof has not landed on `main`, with the sub-issue that unblocks it in the last column. Nothing here is green because nobody looked.

**Every row is `BLOCKED` on the day this file lands, and that is the point.** Ten implementation pull requests were already open when I wrote it, and their tests are named below as the proofs the rows will cite. A row that went green in the same pull request that wrote it would be the failure this file exists to prevent, so no row flips until the pull request that lands its proof on `main` has also had its falsification run and watched to fail. The last column says which sub-issue that is, and the pull request that carries the proof today.

`docs/EPIC-Q-recovery-and-assurance.md` is the contract. Its phase exit gates are the checkbox lists this file numbers `Q1.n` and `Q2.n`, in order, one row per line. Its section 3 consensus table is `QC-01` to `QC-19`. Its section 6 guard table is the `QV.n` ledger, one row per guard, in order.

## How to read a row

| Column | Means |
|---|---|
| ID | `Q1.n` and `Q2.n` for exit-gate lines, `QC-nn` for the adversarial-review findings, `QV.n` for the planted-violation ledger |
| Claim | What is asserted, in the epic's words |
| Executable proof | What will be cited once it is on `main`. `<package dir>:<TestName>` is a Go test in that directory; a bare path is a file. Where no proof exists on any open branch I say so in words rather than invent a name |
| Falsification | The mutation that must turn the proof red. Where the mutation already exists as a planted control, I name it as it is written in `scripts/bdtools/recovery/selftest.py` (run by `scripts/recovery/selftest.sh`), or as an in-process control test |
| Status | `BLOCKED` now. `PASS` only once the falsification has been run and watched to fail. `PARTIAL` when the claim has a half that cannot be shown from here, with the reason in the row. `BY HAND` for a check nobody can automate, naming who checked what and when |
| Waits on | The sub-issue (and the open pull request carrying the proof today) that has to land first |

## How this matrix is checked

A matrix that can only be read is prose, and `docs/epic-checklist.md` section 1 calls this the item that matters most. So the shape is held to what `core/tests/workflowgate/matrix_test.go` already checks for EPIC L: a table row has an id, a claim, a proof column, a falsification column and a status, and the checker refuses a row with no falsification, a `PASS` with no proof, a status other than `PASS` or `BLOCKED`, and (for `PASS`) a proof that does not resolve against the tree. The Status column here is a bare word for that reason, and the sub-issue sits in a sixth column.

**There is no committed checker for this file yet.** `core/tests/workflowgate` is bound to EPIC L's path and ids, and `core/tests/compat/matrix_test.go`'s table of (spec, matrix) pairs has no Q entry. Pointing either at this file is Go, and #954 is documentation only. What I did instead is in the pull request that adds this file: I ran EPIC L's checker logic against this file in a throw-away copy, with its ids, its resolver and its consensus list swapped for Q's, and I planted a row with no falsification, a row with no proof, a row green under another word and a row naming no sub-issue, and recorded each red. That demonstration is not a gate. The gate is the committed checker that #988 (the matrix finished) has to add, and its first job is to hold two things the EPIC L checker does not: that a row names a sub-issue, and that a `BLOCKED` row's cited issue is still open. The compat suite already has the second (`TestEveryBlockedRowCitesAnIssueThatIsStillOpen`).

## What this matrix does not prove

Stated plainly, because a table of `BLOCKED` cells invites the reader to assume the rest.

- **Any behaviour.** Every row is `BLOCKED`. The test names above are what the open pull requests carry, read from their diffs on 2026-10-11; I did not run any of them for this file, and a name can change before it lands.
- **Composition.** Several of the open pull requests were built apart and disagree with each other on defaults, on notification paths and on who reads the resolved policy (the spec's sections 9 and 10). No row here proves they work together; that is a compose-and-run-the-full-gate step before the first merge.
- **A real NAS or a real provider.** Memory and cost numbers are measured on one host; `docs/site/index.html#honest` is where that stays honest. A recovery measured against provider hardware nobody owns is not claimed.
- **Browser behaviour on a real appliance.** The Suite B cases run against the rig; they are not a store-submission screenshot, which needs real hardware (`docs/submission/screenshots.md`).
