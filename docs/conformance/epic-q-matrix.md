# EPIC Q conformance matrix: artifact recovery, scheduled scrubbing and recoverability assurance

What this file is for, and what it is not. It is not a summary of the work: it is the list of claims EPIC Q makes, each one tied to the test that goes red if the claim stops being true, plus the **mutation that was actually run and watched to fail**. A row says `PASS` only because a named mutation, planted as a real violation in a real product file by a self-test that lives in this repository, turned the named test red, and the row carries the date it was run. A row says `BY HAND` when no self-test plants that violation, and then it says who did what and on which day in the row itself, rather than borrowing a neighbouring green. A row says `PARTIAL` when part of the claim cannot be shown from here, and then it says what is missing and what it waits on. There is no `BLOCKED` row, and `core/tests/assurancegate` fails the build if one appears.

This file landed with #954 with every row `BLOCKED`, which was the point: no row flipped in the pull request that wrote it. It flips here, in #988, the pull request that carries the evidence, and the evidence is the thing each row cites. Nothing is green because nobody looked.

`docs/EPIC-Q-recovery-and-assurance.md` is the contract. Its phase exit gates are the checkbox lists this file numbers `Q1.n` and `Q2.n`, in order, one row per line. Its section 3 consensus table is `QC-01` to `QC-19`. Its section 6 guard table is the `QV.n` ledger, one row per guard, in order.

## How to read a row

| Column | Means |
|---|---|
| ID | `Q1.n` and `Q2.n` for exit-gate lines, `QC-nn` for the adversarial-review findings, `QV.n` for the planted-violation ledger |
| Claim | What is asserted, in the epic's words |
| Executable proof | `<package dir>:<TestName>` is a Go test that has to exist in that directory today, and a bare path is a file that has to exist. The Playwright specs under `ui/shared/e2e/` and the unit tests under `ui/shared/src/test/` are cited by path, since they are TypeScript |
| Falsification | The mutation that turns the proof red, as the specification wrote it, followed by what was run. A quoted label is the verbatim name of a planted violation in `scripts/bdtools/recovery/selftest.py` (run by `scripts/recovery/selftest.sh`: the route, the grant, the cost refusal, the budgets), `scripts/bdtools/assurance/selftest.py` (run by `scripts/assurance/selftest.sh`: the three claims) or `scripts/bdtools/assurance/ui_selftest.py` (run by `scripts/assurance/ui-selftest.sh`: the browser side). A guard test that plants the violation itself is cited by name |
| Status | `PASS`: the falsification was run and watched to fail, on the date the row gives. `BY HAND`: nobody can automate it, and the row says who checked what and when. `PARTIAL`: part of the claim cannot be shown from here, and the row says what is missing. `BLOCKED` is not allowed to remain |
| Waits on | The sub-issue and pull request that carries the proof, or, for a `PARTIAL` row, what has to land for the missing half to be shown |

## How this matrix is checked

`docs/epic-checklist.md` section 1 calls this the item that matters most, and it is gated. `core/tests/assurancegate/matrix_test.go` reads this file and fails when one of the eighty rows the specification numbers has no row, when a proof a row cites does not resolve, when a `PASS` row cites no mutation that exists in a self-test and no date it was run, when a `BY HAND` row does not name a person and a date, when a `PARTIAL` row does not say what is missing and what it waits on, and when any row is `BLOCKED`. The checker is a function over text and a resolver, so `TestTheMatrixCheckerRefusesEveryWayAMatrixCanLie` runs it against matrices broken on purpose, one lie each, and requires it to name every one: that is the mutation self-test a new guard owes. Two more guards in the same package hold what the matrix cites: the no-download boundary sentence has to be in every document that made the promise and the old words have to be gone (`TestTheBoundarySentenceIsEverywhereTheOldPromiseWasMadeAndThePromiseIsGone`), and every link in `docs/` and the site has to resolve (`TestEveryLinkInTheSiteAndTheDocsResolves`).

## What this matrix does not prove

Stated plainly, because a table of `PASS` cells invites the reader to assume the rest.

- **A reachable copy is not a recovered one.** The Stored claim says a copy is recorded and, at the class named beside it, that something looked. An existence check is a HEAD: it says an object of the right size is at that key. Nothing in the Stored column says the bytes can be read, and nothing short of a recovery test says they can be put back to use. That is the whole reason there are three claims.
- **A recovery test says the bytes came back and the operator's validator accepted them.** It does not say the application will start. Restoring into an application stays the operator's responsibility (QC-15).
- **The captures are not a store screenshot.** `docs/site/screens/recovery-*.png` are documentation pictures of the real component tree rendering the mock API. `docs/submission/screenshots.md` needs real hardware, a real installation and a real SFTP source, and a mock must never be substituted there; two of its four rows are back to outstanding because this epic changed those screens.
- **The web client does not yet offer Scrub now or Run recovery test.** There is no `api/v1` route that starts either, so a real deployment's browser shows the equivalent `retnd scrub` command and nothing to click, and the pictures of those controls (`recovery-04` to `recovery-10`) show the design the mock offers.
- **Suite C proves equivalence in both directions except one, the ungated direction.** A recovery completes on a deployment whose destructive gate is shut (QC-01), and the CLI has no gate to be shut, so the two cannot be put side by side on that axis. The browser half is asserted in Suite C (the engine that just completed a browser recovery still answers `403 DESTRUCTIVE_OPERATIONS_DISABLED` to `POST /api/v1/operations`) and in `apps/common/webhost:TestARecoveryCompletesWhileTheDestructiveGateIsShutAndOperationsStillRefuses`. The matrix does not claim the CLI side of that axis, because there is nothing there to claim.
- **Composition.** The pull requests were built apart. Where they disagree (the specification's sections 9 and 10), this file says so in the rows it affects (Q1.21, and the 4-versus-2 modes of the per-set control in Q2.2) and does not paper over it.
- **A real NAS or a real provider.** Memory and cost numbers are measured on one host, named in the row; a recovery measured against provider hardware nobody owns is not claimed.
