Recovery and assurance: three claims, five not-a-pass states, one recovery path

Issue #984 (Q2.1), dated 2026-10-10. Parent epic #953, FR-72. Drawn against the screens that ship today (docs/design/Backup Manager.dc.html is the authority where this note and the build disagree) and in the token set from ui/shared/src/design-system/tokens.css. Every surface below is drawn four times: light, dark, and the narrow layout in each. This note writes no TypeScript. It records the decisions Q2.2 (#985) implements rather than reinterprets.

Vocabulary. The labels are Recover artifact, Export, Scrub and Recovery test. The other word for getting data back already means two other things in this product (the archival thaw, and the repository extract), so it is not used as a label for anything here.

1. Backups list and Backup detail: three claims, never one tick

Decision. A backup row carries three separate facts in a fixed order: Stored, Content verified with its own age, Recovery tested with its own age. They are three chips with three labels. There is no roll-up, no combined badge and no summary tick anywhere on the row or in the detail header, because a roll-up is exactly where a checksum pass and a validator failure get averaged into green. A checksum pass with a validator failure reads, literally, Content verified 2d ago next to Recovery test failed 2d ago.

Why the chip is not coloured text. The chip ink is always the body text colour. The state lives in the glyph shape, the border style (solid, dashed, dotted, double) and the words, with colour as a fourth, redundant cue. That keeps every chip at body-text contrast in both themes and keeps it legible to someone who cannot tell the hues apart. --text-3 is never used for text in this note: it is below 4.5:1 on the surface colours in light and in dark.

Computable only. The ages come from placements.verified_at and the per-copy fields Q1.1 adds (next_due, last_failure_at, consecutive_failures, bytes_read, duration_ms, requires_restore). The class that was achieved is shown, never the class that was asked for: a copy that only reached existence shows Stored and Existence checked, and never Content verified.

2. The not-a-pass states, each as itself

Decision. Five reasons produce a not-a-pass, and a two-state chip would render four of them as a pass. They are five values with five renderings: never configured (dashed grey box, a dash glyph, says assurance is off for this set), never run (plain hollow circle, says it is configured and has not run yet), overdue (solid amber, a clock, shows the age it last passed and how late it is), refused for cost (dotted amber, a coin glyph, says the scheduler declined because the read would cost egress and nobody acknowledged it), could not complete (double red border, a warning triangle, says the check started and did not finish, which is not the same as failing). Failed is a sixth, red and solid with a cross: the check finished and the bytes were wrong.

Unknown is its own state, and it is due. unknown (dashed blue, a question mark) is what a rebuilt catalog or an un-migrated copy shows. No rendering path leads from it to the pass chip: the pass chip is only drawn from a record that carries an achieved class and a timestamp, so there is nothing for rendering alone to promote. A prop-driven test cannot prove that, so Q2.2 drives it through a real catalog rebuild.

requires_restore and "no readable copy". An archived object is Archived: thaw needed (solid blue with a heavy left edge, a box glyph) and offers the cost decision in section 3. A set with no copy that can be read at all is No readable copy (solid red, wavy underline, a slashed circle) and offers nothing, because there is nothing to recover from. Neither can be mistaken for Content verified, and a copy in either state never counts towards a satisfied policy.

3. Recover artifact: target chooser and the archival cost decision

Decision. Recover artifact opens a dialog with three targets: Download in this browser, Staging path on the host, Configured destination. The staging root is not editable here (it is a host setting, section 4); the operator picks a sub-name only. The command that does the same thing is echoed under the form by CommandEcho and updates as the target changes.

The thaw cost is a blocking step. When the chosen copy is archived, the dialog replaces its footer with a decision panel: the provider, the retrieval tier, the estimated egress and the time the thaw takes, stated as the provider states them, and two buttons of equal weight, Pay for the thaw and recover and Do not recover. The primary action is not reachable by Enter from the target chooser, it is disabled until the operator ticks I accept this cost, and Escape means Do not recover. It is a dialog the operator has to answer, not a toast they dismiss. A scheduled scrub never reaches this panel: no scheduled pass thaws.

Plain http. The browser path streams to a download; it does not depend on the Clipboard API. Where the command echo offers a copy button, the fallback is a selected, read-only text field.

4. Settings: the global Assurance card, the per-set section, and the four deployment-wide knobs

Decision. The global card states the smart default in a sentence an operator can read without opening a manual: what runs by default, how often, and what it will never do on its own (thaw, or read bytes that cost egress). The per-set section sits beside the retention card in the same shape and offers Inherit, Off, Required, Custom. Inherit shows the value it currently resolves to, as the retention card does, so a global edit is visibly the thing that moved the set.

The written "no". Recovery staging root, staging TTL, concurrency ceilings and the web download memory budget are properties of the host and the process, so they are drawn on the global card only, as deployment-wide readouts with a lock, and there is no per-set control for them. A per-set override could not be honoured by one staging filesystem and one HTTP server. The readouts are drawn on purpose so the absence is visible and nobody later "fixes" it. They are facts, not inputs: no pop-up, see section 8.

5. Scrub now, Run recovery test, live progress, operation detail and the download

Decision. Scrub now and Run recovery test sit in the set's Assurance section. Starting one adds an entry to the active-operations strip and a line to the docked terminal for every named stage; the strip shows the current stage and, for a download, bytes so far. A reload re-reads the durable feed and shows the same stage and the same byte count, and does not start a second run. The operation detail view follows the live stage by default, has an explicit Following toggle, and has Cancel that says what it will leave behind.

Three ways this screen could lie, and what it draws instead. A scrub that fails while Content verified is on screen replaces that chip with Content check failed. A cancelled download ends as Cancelled: nothing saved, a failed one as Failed: nothing saved, and neither is ever drawn with the pass chip or a download-complete link. The pass chip cannot be reached from unknown.

Feed volume. One durable event per scrub pass (with counts) and one per failure. Per-copy progress is live-only and not persisted, so a thousand due copies write two kinds of line, not a thousand.

6. Validator result and log access, bounded

Decision. The recovery-test result carries the validator's exit status, its duration and a bounded tail of captured output in the read-only terminal pattern from #815. Control and window sequences are displayed inert as visible escapes, never interpreted. When the bound cut the output, a marker line is drawn in its own dashed box with italic text, a shape the validator's own output cannot forge because the viewer draws it outside the content stream.

7. Dashboard: due, overdue and degraded

Decision. Three counters in the same chip vocabulary: Due (includes unknown, since unknown is due), Overdue and Degraded (failed, could not complete, or no readable copy). A zero is drawn as a zero with the age of the last pass, never as a green tile, because "nothing is due" and "nothing has ever run" are different statements. Each counter links to the Backups list filtered to it. There is no assurance report and no alert-history screen: both are non-goals of the epic.

Screens that do not change. Activity gains the stage lines described in section 5 through the existing feed. Quarantine and the Backup Set list gain nothing in this note. Settings and the Backup Set detail are sections 4 and 5.

9. Drawn as absent

Figures in the pictures (ages, sizes, the 12 hour thaw, the ceilings) are examples of what the named fields hold; the real defaults are Q1.4's to set and the thaw figures come from the provider response. No assurance report, no alert history, no per-set staging or concurrency control, no per-copy progress stored in the feed, no action for rebuilding the application itself, no combined health score, and no estimate of recovery time for a non-archived copy (nothing computes one). Where a number is not computable, the row is missing rather than showing a placeholder.
