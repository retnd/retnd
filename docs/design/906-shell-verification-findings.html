One cell per script, and it is a button. The shipped table already carries Order, Script, Where, Runs on, size and sha256 for every discovered hook; the only column #906 adds is the verdict of the shell rules on that one file, and the only thing it has to do is get an operator to the findings. So it is a real button with a chevron, not a coloured label: it is reachable by keyboard, announced as pressed for the selected row, and the row it belongs to is marked by an inset rule as well as a tint.

The cell states the worst severity and counts the rest. 1 error, 4 more rather than 5 findings, because the number an operator needs from a table is whether this file has something that blocks a save. A cell that added five findings into one neutral number would make the error and the missing shebang look like the same fact.

"Not examined" is not "clean", and its cell does not open. A hook above the byte ceiling the rules read (this deployment has raised workflows.max_script_size_bytes) was never walked, so there is nothing to open and nothing to claim: the cell is a dashed, inert pill and the findings list carries the engine's own sentence saying how many bytes it is and how many were read. The L7 rule holds unchanged — a green tick for a check nobody ran would be this product claiming it proved something it never looked at.

The findings list keeps its L7 shape and its L7 check ids. The per-script sentences arrive under local_bash_syntax and remote_bash_syntax, the ids that already existed, with the first finding named by code and position and the rest counted. One line per script, never one line per finding: a deployment with sixty-four hooks and an unquoted expansion in each of them would bury the one rm -rf that matters.

Grouped by severity, sorted by severity, and the order is the product's order. Error, warning, info, style — the four severities the rules emit, each with a heading that says what that severity DOES rather than how bad it feels. "Blocks a save" and "reported here and saved anyway" is the only distinction an operator has to act on, and a flat list sorted by line number would hide it behind whichever mistake happens to be near the top of the file.

Every finding shows the line it is about, from the script an operator wrote. A code and a 24:10 is a coordinate; the line with a gutter and a caret under the column is the finding. The excerpt is the script's own bytes as they were captured and hashed for this report, elided where a rule is about two distant lines (BSH004 is about the set -e at the top and the pipeline at line 31, so both are shown). It is inert text in a dark panel, never an editor: this product does not write an operator's hook, and in particular never injects set -e into one.

A message may quote the script's own text and a variable NAME, never a value. $STAGING, $dest and $PGDATABASE appear because they are what is written in the file. Nothing on this screen resolves a variable, so there is no path by which a credential passed through the workflow environment could arrive in a finding.

The header says "parses" before it says anything else. A script that does not parse has no findings at all — the rules walk a tree, and there is no tree — so the panel for 30-tag-snapshot.remote.sh shows the parse position and the parser's own sentence instead of this list, and does not imply the rules found nothing.

The refusal names the script, its stage directory and its scope, because that is what an operator has to go and open. "A script does not pass" with no path is a message that sends somebody looking through two directories by hand. Each refused script is drawn with its file name, the directory it was discovered in, whether that is the deployment's global-before stage or this set's own, and each blocking finding with its code and its line:column.

The sentence about what does not block is part of the refusal, not a footnote. An operator whose save was refused with five findings on screen will otherwise read all five as the reason and go and fix an unquoted expansion that was never the problem. So the panel says which four were saved-and-reported and which one was not, in those words.

The form keeps the edit. The refusal is a rejected write, not a navigation: the fields stay as they were typed, marked as changed, so an operator can fix the script on disk, check again and press Save without retyping anything. And the whole change is refused rather than the parts of it that are unrelated to the bad script — a partly-applied workflow configuration is a shape neither this surface nor the API promises.

There is no override. No "save anyway", no checkbox, no confirm-twice. The two things that are refused are a file bash cannot parse, which a run refuses anyway, and a recursive forced delete of a root-level path, whose failure mode is instantaneous and unrecoverable and whose fix is one character. A control that let an operator past those would exist for no case worth having.

the decisions this note was asking for a verdict on

Why three revisions to one card and not a new screen

Everything here is a fact about a script that is already a row in a table an operator is already looking at. The shipped Workflow panel discovers the hooks, hashes them, and reports two verdicts and a findings list; L7.5 adds one more thing known about each of those rows. So the table gains a column, the column opens a panel about one script, and the save path gains a refusal — and nothing gains a second place to look. A separate "Shell verification" area would be a screen whose relationship to the set's own hook list an operator has to work out, and two lists of the same scripts that can disagree about what was discovered.

The findings panel is the one part that is a screen of its own rather than an expansion in place, and it is a screen for one reason: a finding needs the line it is about. Five findings, each with a source excerpt, inside a table row would push the rest of the set's page off the screen every time somebody clicked a cell out of curiosity.

Decisions taken

  • The findings cell states the worst severity and counts the rest. 1 error, 4 more, not 5 findings, and not a bare colour.
  • Four severities, four groups, in the product's order — error, warning, info, style — each headed by what that severity does to a save rather than by how serious it sounds.
  • Every finding carries the script's own line, with a gutter and a marked column. Inert text on the dark surface the run terminal uses, never an editor: nothing in this product rewrites somebody's hook.
  • "Not examined" has its own state, its own reason sentence, and no verdict. Its cell does not open, because there is nothing behind it, and it does not refuse a save.
  • "Clean" says what was applied and that nothing ran. Six rules, named, over bytes that were parsed and walked in the engine process.
  • A script that does not parse shows the parse position, not an empty findings list. The rules walk a tree; with no tree there is no claim to make.
  • The refusal names script, stage directory, scope and each blocking finding with its position, and says in the same panel that warnings, info and style did not block.
  • The refused save keeps the operator's edit in the form, marked as changed, and refuses the change as a whole rather than applying the parts of it that are innocent.
  • No override on the refusal. The two blocking conditions are a file a run would refuse anyway and a root-level rm -rf.
  • The copy says these are backupd's own rules. BSH, never SC, and the word ShellCheck does not appear on any surface: these are six rules of this product's own, and a code that looked like somebody else's would send an operator to documentation for analysis this product does not perform.

What this inherits rather than invents

No new component vocabulary and no new tokens: the card, header, pill, tag, table, banner and finding-row shapes are #814's, the source excerpt reuses the run terminal's --term-* surface from #815, and the two verdict badges, the on-demand Check this set's hooks button and the local_bash_syntax / remote_bash_syntax check ids are the shipped ones, carrying one more sentence each. Colour is never the message: every severity pairs a word with a shape, which is the reading a colour-blind operator gets. The findings column collapses under the script name at narrow widths, and each cell is a real button so the panel is reachable by keyboard and the selected row is announced as pressed.

On the wire this is one added object on each discovered script — lint: { examined, not_examined_reason, parsed, parse_error, parse_error_line, parse_error_col, findings[{ code, severity, line, col, message }] } — and the refusal is an HTTP 409 with the error code WORKFLOW_SCRIPT_REJECTED carrying the blocking findings as fields. The screens above draw those fields and compose no sentence of their own out of them, so the CLI's validate workflow and this panel cannot end up describing the same script differently.
