The selected step's log terminal mounts here, and only here: one terminal on the page, created when a step is selected and torn down when the selection moves. The slot is a component boundary with a fixed shape — { runId, stepId, step, api } — so the hardened read-only terminal (#815) drops into it without this page knowing how it streams.

Three verdicts, three columns, and none of them derived. "The backup succeeded and the cleanup did not" is the single most operationally important thing this feature can report — a machine may be sitting quiesced with a good backup beside it — so the header shows Backup: Success next to Workflow: Failed and names the cause script. A page that showed one badge would make that state unsayable, which is the same argument L6's handler doc makes for the journal having three columns.

Every .local.sh row says "Local Host" and names the Host Workflow Runner. Never "engine container", never "inside backupd": the runner is a component on the machine backupd is installed on, and a row that implied the engine container grew a shell would be describing a deployment shape this product does not have.

Every script name states where it runs. A hook is NAME.local.sh or NAME.remote.sh and nothing else: core/internal/workflow/script.go refuses a plain *.sh outright, because "a hook that quiesces a database has to run on the machine holding the database, and guessing wrong is silent". So the rows here carry the suffix, and the Local/Remote badge agrees with it by construction rather than by convention.

The short SHA column is an em dash on purpose. L6's run-step shape carries no sha256 — only the validation report does, for scripts as they are on disk right now. Printing today's hash in a row describing a run from last night would be a lie about what executed, so the column stays empty until the journal carries the planned hash.

The five stages are always all five, even the ones this configuration gives no directory to. A stage rendered only when it has steps would make "global after did not run" and "this deployment has no global after directory" the same picture, and those are opposite facts when a source has been left quiesced. An ineligible stage is drawn greyed with "no directory configured" rather than omitted.

A canceling run is not a finished one. The header carries both words — canceling, and cleanup running — because the interesting thing about a canceled workflow is that its after hooks are still owed. The per-set Run control is unavailable while this is live, and says why.

The hold blocks the Run control and nothing else. A set in recovery_required keeps every read on this page — an operator diagnosing a hold needs the configuration, the validation and the run that caused it — but the ordinary per-set Run is unavailable and the banner is the only thing that offers a way out of it. Two ways out, deliberately: Resume cleanup executes the hooks that are already owed from that run's own retained spool (re-verified against the sha256 recorded when it was planned, so nothing an operator edited since decides what runs), and Acknowledge records a person taking responsibility in words that are kept. There is no "dismiss" and no "ignore".

A set with no workflow configuration shows none of this. No panel, no findings, no empty table — one line saying hooks are not configured for this set and where they would go. New noise on every existing set is the failure mode this whole screen is one edit away from.

Two verdicts, kept apart. valid_for_backup and workflow_valid are reported separately, because a set whose source connects and whose hook directory nobody has created yet is valid for backup and invalid for workflows — the normal state during setup, and reporting it as a broken backup set would tell an operator their backups are failing when they are not.

No surface here can show the value of a secret, ever. The wire carries a LOCATION — a file path, a variable name, an argv — and there is no field on the contract a resolved secret could travel in. So the editor shows the name and where the value comes from, and the merged preview shows "resolved from a file at run time" in the cell where a literal would be. A reveal control would be a control an attacker holding one session could read every credential in the deployment from.

An empty literal is not a missing one. value: "" is a deliberately empty variable, which operators write, and no literal at all is a variable whose value comes from a reference. The table draws them differently and the write direction keeps them apart.

The preview is source-aware because precedence is the whole question. Two tables, not one: the top one is what is configured and editable, the bottom one is what a hook actually receives, with the scope that won and what it shadowed. An operator who cannot see that a set-scope PGHOST is hiding the deployment's has no way to explain a hook connecting to the wrong host.

"Not examined" is not "passes". A local hook's syntax check runs through the runner, so with the runner down the honest answer is that nothing looked — a green tick there would be this product claiming it proved something it never ran. The same rule covers a deployment with no remote hooks and an unexamined exec capability.

No root-elevation control. The execution user is reported because an operator writing a hook needs to know what account it runs as; there is no switch here that would raise it, because that switch does not exist in the product and a UI offering one would be inventing a capability.

the decisions this note was asking for a verdict on

Why these five screens and not a "Workflows" section

Every surface here is a sub-resource of something already on screen. A run belongs to a backup set; the configuration that produced it belongs on that set's page beside its retention and its connection; the deployment-wide half belongs in Settings next to the other deployment-wide policy. A separate top-level "Workflows" area would be a second place to look for the state of one backup set, which is how two screens end up disagreeing about what is configured.

The one exception is the run itself, which is routed top-level (/workflow-runs/:runId) for the reason L6 made it a top-level resource: a run outlives the configuration that produced it, so a set whose configuration has been removed still has runs an operator needs to read.

Decisions taken

  • Three statuses, three columns, never folded. Backup, Workflow and Cleanup are shown side by side with the cause script named. This is the screen's reason to exist.
  • One terminal, lazily mounted, in a slot with a fixed prop shape. Selecting a step mounts it; changing the selection tears the old one down. A page that mounted a terminal per step would hold one poll per script of a run that can have dozens.
  • All five stages always, ineligible ones greyed. "Did not run" and "not configured" must not look the same.
  • "Local Host", via the Host Workflow Runner, everywhere. Never "engine container".
  • The recovery hold gates the per-set Run only, and offers exactly two ways out: Resume cleanup, or Acknowledge with a recorded reason.
  • Termination-unconfirmed is a page-level banner, not a cell. A step that was signalled and did not confirm is a fact about a remote machine, and a 12px cell in a table row is not where that belongs.
  • Secrets are locations in both directions, with no reveal control, and the merged preview says where the value will come from instead of what it is.
  • Nothing new on a set with no workflow configuration beyond one line saying so.
  • The short SHA column stays empty for a run. The journal does not carry the planned hash; the validation report's hash describes disk now. Rendering one as the other would be a lie.

Built inside the existing design system

No new component vocabulary: card/card__header/card__body, PageHeader, Section, StatusBadge, WarningBanner, EmptyState, Cell/Row and the design-system tokens carry every screen above. Colour is never the message: every status pill pairs a word with an icon, which is the §9 rule and the reading a colour-blind operator gets. The step ladder collapses to a single column at narrow widths, the selected step is marked by an inset rule as well as a tint, and the selection is a real button so it is reachable by keyboard and announced as pressed. Every new control names a tooltip registry id rather than carrying its own copy.
