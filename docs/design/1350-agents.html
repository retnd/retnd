The Agents card: tokens, a token shown once, confirmations a person approves, and the audit

Issue #1350 (U2.2), dated 2026-11-11. Parent epic #1343 (EPIC U), FR-93 and FR-97. I drew it against the EPIC U specification (docs/EPIC-U-mcp-server.md, PR #1354, section 12 for the names) and against what already ships, because the design needs those and not the implementation, which does not exist yet: there is no core/agenttools and no agent route on main today. #1351 (U2.3) builds the card from this note and from nothing else, so every sentence below that a build would have to take on trust is listed in section 14 with the issue that owns it. Drawn on the shipped screens (the first design canvas in this directory (the oldest .dc.html, introduced in docs/design/README.md) is the authority where this note and the build disagree) and in the token set from ui/shared/src/design-system/tokens.css. Every surface is drawn four times: light, dark, and the narrow layout in each. This note writes no TypeScript and no tooltip copy that ships; the field-help sentences in section 10 are proposals U2.3 checks against the code it lands beside.

Vocabulary. The words are Agent, Token, Scope (read, operate, configure, always in code type, always lower case, because they are the closed words the API and the CLI use), Active, Expired, Revoked, Waiting for you, Approve, Deny, Audit. A token is never a key on this card, because "key" already means key material in this product (EPIC N) and nothing here is that. An agent is never trusted or verified anywhere on the card: the whole epic exists because it is neither.

Status: a mock-up, superseded where the product differs.

This is a picture drawn on 2026-11-11 to settle decisions for U2.3 (#1351). It is not the product and it is not kept in step with it, so where the two disagree the product wins, and the build's own CSS and strings win over anything drawn here. Tokens, names, dates, ids and command lines are examples of what the named field would hold. The command lines in the echo blocks are the shape core/cliecho will print: CommandEcho shows what the response carries, so none of the strings drawn here are copied into the build. The token itself, in section 4, is a stand-in: the format is #1345's, and the string in the picture is not one.

1. The card, at rest: a statement, then four regions

Decision. One card on the Settings page, titled Agents, in the shape of the Retained-copy encryption card (EncryptionCard.tsx): an eyebrow heading carrying its TooltipId, a body of regions separated by rules, and a CommandEcho under every action. It sits directly after Retained-copy encryption and before Workflow, with its own anchor (#agents, a new SETTINGS_SECTIONS entry). The reason for the place: encryption is "what a copy is", workflow is "what runs around a copy", and agents are "who else can ask"... which belongs after the things they would be asking about and before the housekeeping at the bottom (Interface, Catalog recovery, Platform, Password). It is not a page of its own because the issue is about a card, and because a second place to find "who can reach this deployment" would sit beside the Administrator password card, which is where an operator already looks for that sentence.

The statement comes first and says three things. What an agent is (a client of this deployment with a token of its own), what it can do by default (look, and nothing else), and what it can never do without you (anything an operate or configure token asks for waits in the confirmations list until you approve it with your password). The fourth sentence is the limit I would rather state than leave out: an agent is not given key material, recipients, credentials or secrets, and the audit records every call it makes, reads included. That sentence is FR-98 and FR-97 in the card's own words, and it is only allowed to stay on the card while U1.5 and U2.4 prove it (section 14, row 1). I did not write "safe", "protected", "secure" or "trusted" anywhere on this card: the spec's own closing paragraph says what it does not prove, and a word that says more than that would be the invented claim the checklist warns about.

Four regions in the order a person uses them. Tokens first (who can connect), Pending confirmations second (what needs me now), Audit third (what happened), and the HTTP transport statement last, because it is a fact about the deployment and not a task. The mint button lives in the Tokens region heading row, not as its own region: minting is the one act in the card that changes who can connect, and it sits where the list it extends is. When something is waiting, the confirmations region is not reordered above the tokens ("the dangerous thing jumps to the top" was considered and rejected: a list that reorders itself moves the Approve button under a cursor that was already travelling to it). Instead the card heading row carries a count, 1 waiting for you, that is a link to the region, and the Dashboard health card is not touched (the epic names no health fact for agents, so I draw none).

Not a table of everything. The tokens table carries exactly the nine columns the issue names. The audit table carries exactly its six, plus a per-row Details disclosure for the two fields FR-97 also names (arguments after projection, and transport). Nothing is added "because it would be nice": a column the response does not carry is a column somebody computes in the browser, and the checklist's engine rule (section 3) forbids that.

2. What each scope can call: read from the catalogue, never copied

Decision. A disclosure under the Tokens heading, What each scope can call, closed by default, that lists the tool names by scope exactly as GET /api/v1/agent/tools returns them. The names drawn in section 2 are the ones in section 12 of the spec at 9cd53e1f plus PR #1354: 19 read tools, 7 operate tools and 4 configure tools. They are a stand-in for the response and U2.3 renders the response (TestTheCardListsWhatTheCatalogueLists is #1351's guard). If U1.3 lands a catalogue with a different set, this picture is the one that is wrong, and it stays wrong on purpose: the note is dated.

Why it is on the card at all. A scope word means nothing until you can see what it lets an agent reach, and the mint dialog's one-sentence descriptions (section 3) are deliberately generic ("ask for backups to be started or checked") so they cannot drift from the catalogue. This is where the specific list lives. It is a closed disclosure so the card is short by default, and it is plain text in code type: no buttons beside the names, no per-tool toggle (the spec's non-goals rule out per-tool and per-set restriction, so a toggle would promise a thing the code cannot do).

What it does not say. It does not say whether an operate token can also call the read tools. The spec says a read token starts nothing and changes nothing, and does not say the other direction in words; the catalogue row carries one scope per tool. So the disclosure is a table of "tools whose scope is X" and carries no sentence about inclusion until #1345 or #1346 states it (section 14, row 4). It has since: scopes nest, and the mint copy says so, but the disclosure still carries no sentence of its own. The same goes for the routes the catalogue refuses (key export, authentication, credentials, recovery grants, token minting): they are refusals with a stated reason in the catalogue, and the card does not list them, because a list of what is refused is a list of what to try.

3. Mint: a name, a scope that defaults to read, an expiry that defaults to 90 days

Decision. Create token opens a dialog with three fields and nothing else: Name, Scope, Expires in. The scope group shows read selected with its sentence (it can look, and it cannot start or change anything), and a fold underneath, Allow more than reading, closed by default, that holds the other two radios with one sentence each. The fold is a real fold and not a nag: the epic says read is the only default and "nothing in a wizard, a setting or a prompt suggests more" (core invariants), so the dialog never recommends, pre-selects or sorts operate and configure above it. Opening the fold changes nothing but visibility; a token minted with the fold closed is a read token.

The two sentences are honest about the human in the loop. operate: "Can ask for backups and checks to be started. Nothing runs until you approve each request here." configure: "Can ask for a backup set to be enabled or disabled, or its retention or assurance settings changed. Nothing changes until you approve each request here." Both are statements of FR-95, neither names a tool (so neither can disagree with the catalogue) and neither contains the word "safe". The sentences live in the tooltip registry under agents.mint.scope.operate and agents.mint.scope.configure and the dialog reads them from there.

Expiry is a duration the engine judges. The field takes the same duration word the CLI takes (--expires-in 90d), starts at 90d, and the browser validates nothing: the ceiling (one year) and the shape are U1.2's refusals, and the dialog shows the engine's message as written, in the field's own error slot, with the field's edge turned to a two-pixel danger line plus the words, never colour alone. I considered a date picker or a select of 30, 90 and 365 days. A select would be a second copy of the ceiling in TypeScript and would be silently wrong the day the ceiling moves; a date picker invents a timezone question the CLI does not have. The refusal row in the picture shows the shape: the message and code are the server's.

The name. It becomes agent:<name> in every actor field (FR-91), so the dialog says that under the field. What characters a name may hold is #1345's rule, not mine; the dialog shows its refusal as written. No "generate a name" button.

The transport consent. A token is the longest-lived secret this product hands to a browser, and the mint response is the one time it crosses the connection. The existing insecure-transport consent (acknowledgeInsecureTransport, ui/shared/src/api/client.ts) only guards the step-up password today. I propose the mint submit asks the same question first, from the same function, when the capabilities say the connection is not encrypted: no new control, no new copy, the prompt that already exists. This is a decision for review (section 14, row 7), not a given: if the reviewer thinks the existing prompt's wording is about passwords only, the wording needs one more sentence and that is #1351's to write.

4. The token, shown once, and the only way out of that dialog

Decision. On success the dialog changes in place to show the token in a read-only mono field with a Copy button beside it, a plain sentence that this is the only time it is shown, the command that made it (retnd agent token create ..., composed in the browser), and one button, I have stored it. That button is the only way out: there is no close glyph, no Cancel, the backdrop does not dismiss, and Escape does nothing. Focus is trapped in the dialog and lands on the copy field on open, so a keyboard user can copy before anything else, and the selection is not changed by the dialog closing in a way that loses it (nothing closes it). Dismissal by any other route would let the token vanish unread, and the only recovery would be to revoke and mint again. The cost of this rule is real and I am stating it: an operator who reloads the page, or whose browser crashes, with the dialog open has lost a token they never saw. The dialog says so ("If this page is closed before you store it, revoke the token and make another"), because the alternative, a recoverable token, would mean the plaintext is stored or can be re-derived, and FR-91 says it is neither.

After the click, the prefix is all the card ever shows. The new row appears in the tokens table with its eight-character prefix and nothing else of the secret. #1351's falsification is the picture's rule: the token string is in the DOM for the life of this one dialog and in no list row, tooltip, toast, live region, title attribute, error message or browser storage, before or after. The copy button writes to the clipboard and announces "Copied" in a polite live region that does not contain the token. The echo line shows the command with the name, scope and expiry the dialog was given, and it is already there while the form is being filled in (it is composed, so it needs no response); the token is not in it and cannot be: the CLI prints the token to the terminal once, and the web echo shows only the twin of the act.

What the dialog tells the operator to do with it. One line of plain text, not a control: use it with retnd agent serve --stdio --token-file PATH (a file readable only by you) or the RETND_AGENT_TOKEN environment variable, and never on a command line. That is FR-96 and D3 of the spec. The line has no copy button, because there is no way to type a real path for the operator; it is a statement of how the token is used.

Considered and rejected. A checkbox that arms I have stored it, as the bundle export dialog does (I understand this file can decrypt every copy). The bundle checkbox exists to make a person read a risk before a download. Here the button's own label is the acknowledgement, the issue says it is the only way to close, and a checkbox would add a second control to a dialog whose point is that there is one way out. Also rejected: showing the token masked with a reveal toggle, because a mask invites a screenshot of the unmasked state and a toggle is a control the code cannot give a different effect to.

5. The tokens list, every state, and revoke

Decision. One row per token, nine columns in the order the issue names: name, prefix, scope badge, owner, created, expires, last used, status, and the action cell. The name column shows the name and, beneath it in the secondary ink, the principal as it appears everywhere else, agent:nightly-triage, so an operator reading the audit can match the two without a lookup. The Expires cell shows the date and, beneath it, the time left ("in 76 days") or, for an expired token, how long ago ("49 days ago"). The relative wording is display only: the date is the server's, the browser formats the difference, and nothing is decided from it.

Three statuses, three renderings, none of them only colour. As in #984 and #994: the ink is always the body text, the state is carried by the glyph shape, the edge style and the word, and colour is the redundant fourth cue. Active is a check on a solid green edge. Expired is a clock on a dashed neutral edge (a token that ran out of time, nothing wrong with it). Revoked is a slashed circle on a solid red edge (a person ended it). Expired and revoked rows stay listed, in the same ink as active ones: dimming them with opacity would take their text below 4.5:1, so the distinction is the chip and not the row. Last used reads never for a token nothing has presented.

Revoke is one button on an active row, and it asks. Revoke opens the existing ConfirmationDialog with the consequence in the button: Revoke agent:nightly-triage, and a sentence that its next request is refused (the engine checks revocation on every request, FR-91) and that a revoked token cannot be brought back, only replaced. No typed phrase: the shipped component reserves that for confirmations reached from a list where the near-miss is the danger, and the near-miss here is cheap, since a wrong revoke costs one mint. The row does not offer Revoke when the status is already expired or revoked: there is nothing the code does for it that the status has not already done. The echo, retnd agent token revoke ID, is composed in the browser, since the list response carries no twin (section 14, row 6).

No edit. A token's name, scope and expiry cannot be changed after minting: the spec has no verb for it ("Token rotation. Mint a new one, revoke the old one", section 8). So the row has no pencil, no extend button and no scope switcher. The honest path to a longer-lived token is the same two clicks as the CLI's.

6. Pending confirmations: who asked, what, until when, and Approve or Deny

Decision. One row per pending record, newest first. A row says, in this order: the sentence (the catalogue's static description of the tool, in the product's own words), who asked (agent:recovery-drill), the exact retnd command the request will run, drawn as a copyable code line (the record's own command, never composed in the browser), the backup set it is about, when it was asked, and when it expires, with the buttons Approve and Deny. It does not draw the request body or any JSON: the command is the words an operator already reads, and the spec (expert 4) is explicit that a dialog showing a blob is a dialog that gets approved by reflex.

Approve opens the step-up and calls nothing. Pressing Approve expands the row to a password field ("Your password", the shipped StepUpPassword wording: sent once with this request and not kept) and a primary button, Approve and run, disabled until the field has text, and a Cancel that collapses it. The route is not called until the password button is pressed (#1351's network-watching spec). The password travels as the existing step-up header and is held for that one request, as the bundle dialog does; on a connection the capabilities call unencrypted the existing consent prompt runs first, so the password is never the first thing to cross. The button says run because that is what approval does: it replays the recorded request byte for byte (FR-95), and no body is supplied at approval, so the UI sends none.

Deny is one click and no password. Denying executes nothing and cannot hurt, so it asks for nothing. It sits beside Approve as a neutral button, not a danger one: Deny is the safe answer and must not look like the risky one. Both buttons are the same size and the same weight apart from the primary fill that appears only after Approve has been pressed, so the row never visually recommends running the request.

Seconds from expiry. The expiry reads expires 09:53 (in 0:41) and, under a minute, the row takes the two-pixel warning edge and the clock glyph. The countdown is the browser formatting a server time. It does not disable Approve when it reaches zero: the browser's clock can be wrong, and the server is the judge. If the operator presses it late, the engine refuses with AGENT_CONFIRMATION_EXPIRED and the row shows that sentence as written, then falls out of the list on the next load into the audit. A client that locked the button on its own clock would be a second implementation of expiry.

Refusals are shown in the row, in the engine's words. Four things can come back at approval, and each is drawn: the step-up refused (wrong password, or the step-up rate limit), the confirmation expired, the engine unreachable, and the one the issue singles out, the shut operation gate. For the gate the row switches to a result strip with a two-pixel danger edge: the gate's own sentence verbatim (destructive operations are refused over HTTP in this release, until the trusted-proxy authentication gate (issue #92) has been verified; run the equivalent retnd command on the host), the code DESTRUCTIVE_OPERATIONS_DISABLED, exit 50 (what the CLI would have exited with for the same refusal, FR-94), and the correlation id. It is not a toast and it is not a generic "could not approve". The strip stays until the list is next loaded, then the record lives in the audit. It has no control: nothing to dismiss, nothing to retry (the gate is shut by construction, not by a transient fault).

What leaves the list. Approved, denied and expired records fall out of the list and into the audit; the list never shows a decided record except the result strip above for the one the operator just decided. There is no "history" tab: the audit is the history, and it is on the same card.

Not drawn: a per-token pending count, the cap (agents.max_pending_confirmations), and the confirmation TTL. The cap is the agent's refusal (AGENT_CONFIRMATION_LIMIT, which lands in the audit), the TTL is a config value this card cannot change, and neither is a control.

7. The audit: newest first, filtered by token and time, reads included, paged

Decision. A table of calls, newest first, with six columns: time, token, tool, the scope the tool needs, the outcome (the HTTP status and the API's code, in a chip with a glyph), and the correlation id in mono. Above it two filters: Token (a select of the listed tokens plus All tokens) and Since (a duration word, as retnd agent audit --since D takes), and the echo under the table shows the twin for the current filter (retnd agent audit --token ID --since 24h). Reads are rows like any other (FR-97); a read token's day is mostly 200 chips, and that is the point of the table.

Paged the way the feed is. The table asks the route for a page and shows Show older at the foot while the route says there is more (the cursor the API gives, as the Activity feed uses before and next_cursor). It is never truncated and never infinite-scrolls: the append is explicit, so the row under the cursor does not move. There is no total count and no page number, because the route is a cursor, not an offset. A footer sentence says the trail is bounded and older rows are pruned; it does not state the number of days, because the retention (agents.audit_retention_days) is deployment config the card does not read.

Outcome, not exit code, in the row. The row shows what the API answered. The exit code the CLI would have used is the tool result's (FR-94) and the audit row does not store it (the table in the spec has status, code and correlation_id), so I did not draw a column the record cannot fill. The one place the card shows an exit code is the gate-refusal strip in section 6, where the approval response carries it.

Details is a disclosure, not a page. Each row has a Details button that expands the two fields the table has no room for: the transport (stdio or http) and the arguments after projection. The arguments are text an agent supplied, so they are rendered as inert text in a mono block with a bounded height, never as HTML, never linkified, never evaluated; a set name or a file name an agent put there is data and is drawn as data (the same rule the spec holds the tool results to, UC-02). If the audit route does not return the arguments in a form the browser can show, the disclosure goes and nothing replaces it (section 14, row 9).

A read token that tried to change something is the row to notice. AGENT_SCOPE_INSUFFICIENT is drawn as a refusal chip like any other: same glyph, same edge, no extra alarm. The audit is a log, not an alerting surface, and the epic names no alert for it.

8. Empty, error and read-only states

Decision. Every region has an empty state that says what is true and what the next act is, a load-failure state that shows the engine's code and correlation id, and a read-only state. The empty tokens region says No agent has a token. Nothing can connect to this deployment as an agent. and offers Create token: it is the default state of every deployment, so it must read as normal and not as a missing setup step (the epic: a deployment with no token has no agent access and behaves as before). The empty confirmations region says Nothing is waiting for you. and nothing more. The empty audit says No agent has called anything yet.; when a filter is the cause it says No calls match this filter and offers Clear filters, because the two are different facts.

Errors are the engine's. A failed load shows the message and code from the response, the correlation id in mono, and the shipped Retry (common.error-retry). It does not invent a friendlier sentence. A region fails on its own: a failed audit load leaves the tokens and confirmations drawn, since they are separate routes (/agent/tokens, /agent/confirmations, /agent/audit, and /agent/tools for the scope list). A mint that fails keeps the dialog open with the field values kept and the refusal beside the field it is about; the failure of the approve step-up is in section 6.

Read-only. When the page is read-only (readOnly, the version mismatch the other cards already follow), the lists stay readable and every mutating control is absent, as EncryptionCard.tsx does with readOnly ? null : ...: no Create token, no Revoke, no Approve, no Deny. A pending row still reads in full, with the sentence that approving needs a writable page, so an operator who can see something waiting is not left to wonder why they cannot answer it.

9. The HTTP transport: an honest statement, not a switch

Decision. The last line of the card says whether the streamable HTTP transport is off or on, as text, and when it is off, the one configuration line that turns it on. It has no toggle, no checkbox and no button, and it gets no tooltip: a statement of fact is not a control (checklist section 5, "an honest non-interactive statement of fact"). The reason is in the code and in the spec. agents.http_transport is a field of a config block with KnownFields(true), so a configuration that writes it cannot be read by an older build; that is a one-way door, and a web toggle would walk an operator through it on a single click with no way back. Nothing in the planned routes patches agents: from the browser (the routes are tokens, tools, audit, confirmations and the MCP endpoint itself), so a toggle is a control whose effect the code cannot state, which is the checklist's hardest rule. It is also the example the issue gives for the falsification table, and I have drawn the opposite of it.

Off is the default and the picture says what that means. Agents connect with retnd agent serve --stdio, which runs beside this engine. The sentence to turn HTTP on is a configuration line (agents: then http_transport: on) and the line that follows it says what the line costs: the older-build refusal. When it is on, the statement says where it listens (/api/v1/agent/mcp) and what that means on a connection that is not encrypted, in the same words the epic's risk 2 uses: the token travels in a header on whatever connection reaches the engine, so on plain HTTP it is readable on the network, as the session cookie already is.

Where the card learns on or off. From agents_http_transport (on or off) on GET /system/capabilities, which the card already reads for the insecure-transport gate (settled in #1364, section 14 row 3). The line starts with the picture's HTTP transport: on or HTTP transport: off, then the how-to sentence.

11. Reviewed against the first design canvas and the build: what follows them and what deliberately does not

Follows the canvas and the build. Card shape (eyebrow heading on --surface-2, body in regions), the button weights (primary, neutral, danger), the dialog-scrim and dialog shapes from components.css (the scrim is the one colour literal in this note, copied from .dialog-scrim), ConfirmationDialog for revoke (the consequence in the button, as its own comment requires), StepUpPassword for the approval password, CommandEcho under every action, the chip-with-glyph pattern of #984 and #994 for every state, and the token set, all unchanged. The canvas has no dialog that shows a secret once and no list of principals (the word "agent" occurs in it only as ordinary copy), so the card, the shown-once dialog and the confirmation row are additions in its shape rather than reinterpretations of anything it draws.

Diverges, and why. The canvas draws text boxes and segmented controls with --border-strong, which is 1.69:1 on the light surface; this note uses --edge-3 as the shipped assurance and encryption CSS does, so a control edge meets 3:1 (section 13). The build's --text-3 is a text ink at 4.5:1 since #1235; this note uses it for exactly one thing, the text of a disabled button. And one rule here is stricter than any card in the build: the mint dialog has no way to close except the act it exists for. The Retained-copy bundle dialog has a Cancel; this one cannot, because cancelling a shown-once secret is losing it.

What a dialog on this page does about the narrow layout. Tables become labelled blocks below a 640px container (each cell carries its column name in the secondary ink), the pending row's buttons stack, and the key/value lists go single-column. The shown-once token wraps rather than scrolling, so the whole of it is on screen to be read and copied.

No HTTP transport toggle. No per-tool or per-set restriction. No token edit, extend, rename or rotate. No "show token again", no reveal toggle, no masked token, no export of a token, no QR code. No pre-approve, "always allow", "trust" or "remember this choice" on a confirmation. No bulk approve, no approve-all. No request body or JSON in a confirmation. No confirmation count or cap control. The script that produced the table (the same arithmetic as scripts/contrast/check-ui-pairs.py) 
import math, re
# oklch(L C h) -> linear sRGB, then WCAG relative luminance, then (L1+0.05)/(L2+0.05).
def oklch_to_linear(l, c, h):
    a, b = c*math.cos(math.radians(h)), c*math.sin(math.radians(h))
    l_, m_, s_ = l+0.3963377774*a+0.2158037573*b, l-0.1055613458*a-0.0638541728*b, l-0.0894841775*a-1.2914855480*b
    lc, mc, sc = l_**3, m_**3, s_**3
    rgb = (4.0767416621*lc-3.3077115913*mc+0.2309699292*sc,
           -1.2684380046*lc+2.6097574011*mc-0.3413193965*sc,
           -0.0041960863*lc-0.7034186147*mc+1.7076147010*sc)
    return tuple(min(1.0, max(0.0, x)) for x in rgb)
def hex_to_linear(v):
    h = v.lstrip("#"); out = []
    for i in (0, 2, 4):
        x = int(h[i:i+2], 16)/255
        out.append(x/12.92 if x <= 0.04045 else ((x+0.055)/1.055)**2.4)
    return tuple(out)
def lum(c): return 0.2126*c[0]+0.7152*c[1]+0.0722*c[2]
def ratio(a, b):
    hi, lo = sorted((lum(a), lum(b)), reverse=True)
    return (hi+0.05)/(lo+0.05)
def colour(v):
    m = re.fullmatch(r"oklch\(\s*([\d.]+)\s+([\d.]+)\s+([\d.]+)\s*\)", v)
    return oklch_to_linear(*map(float, m.groups())) if m else hex_to_linear(v)
# usage: ratio(colour("#191a19"), colour("#ffffff"))  ->  17.8 (text on surface, light)
