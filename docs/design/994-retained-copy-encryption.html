Retained-copy encryption: encrypted is not recoverable, keys are never shown, the bundle is the only thing that changes the threat model

Issue #994 (N2.1), dated 2026-11-09. Parent epic #967, FR-59 and FR-66. I drew it ahead of the Phase 1 code, against the EPIC N specification (#968, PR #1266) and what already ships, because the design needs those and not the implementation. Section 15 lists what it leans on, so a change in #989 to #993 can be traced back to the picture it moves. Drawn against the screens that ship today (docs/design/Backup Manager.dc.html is the authority where this note and the build disagree) and in the token set from ui/shared/src/design-system/tokens.css. Every surface below is drawn four times: light, dark, and the narrow layout in each. This note writes no TypeScript and no tooltip copy. It records the decisions N2.2 (#995) implements rather than reinterprets, and it was drawn by hand in the per-issue note form that 814-workflow-ui.html, 815-step-terminal.html and 984-recovery-assurance.html already follow.

Vocabulary. The labels are Encrypted, Verified recoverable, Plaintext, Not decrypt-verified, Key missing, Recovery bundle, Managed key, External key reference, Rotate, Verify recoverable. "Verified" on its own is not a label for anything in this note, because the Backup detail page already uses that word for the producer-manifest checksum on the lifecycle rail, and Encrypted is never qualified with "securely", "strongly" or an algorithm name, because the format is a property of the build and no sentence here may claim more than the code states.

Status: a mock-up, superseded where the product differs.

This is a picture drawn on 2026-11-09 to settle decisions for N2.2 (#995). It is not the product and it is not kept in step with it, so where the two disagree the product wins, and the build's own CSS and strings win over anything drawn here. The command lines in the echo blocks are the shape N1.5 (#993) fixes: CommandEcho prints the real verbs and flags from the same function the terminal uses, so the strings drawn here are not copied into the build. Key ids, dates, sizes and destination names are examples of what the named fields hold. No key value, canary, credential or real hostname appears anywhere in this file or its render, and no field drawn here accepts one.

1. Two states that look different: Encrypted, and Verified recoverable

Decision. A copy carries two separate facts about encryption and they are two chips, never one. Encrypted (a filled-box glyph for a sealed copy, a solid neutral edge, the quiet second surface) means exactly what the backend recorded: the committing attempt wrote ciphertext under a named format id and version, recorded the key id it used, and recorded the digest of the stored bytes in the new per-copy column (FR-61). It says nothing about whether anybody can read it back. Verified recoverable (a double check, a solid green edge, the ok fill, always with an age) means a streaming decrypt of the stored object produced a plaintext digest equal to artifacts.local_hash, at the time shown (FR-62). That is the only path to the green chip. Ciphertext existing, an existence check at the recorded size, a provider's own checksum, a lock existing (EPIC M) or a key being resolvable do not reach it.

Why they cannot be one badge. If the product drew one badge for both, an operator would read "encrypted" as "safe", and the backend has proved no such thing: the key could be gone, the object could be tampered or truncated, and the row would still say the same word. placement.Class.Proves() is already the operator-facing sentence for what a verification class proved, and over an encrypted copy a ciphertext-to-ciphertext content check would make that sentence lie in the product's own words. Two chips with two meanings is how the UI stays inside what the backend proved.

The not-recoverable states are each their own rendering. Not decrypt-verified (dotted neutral edge, a hollow circle) is an encrypted copy that nobody has asked to decrypt yet: the honest default, since decrypt-verify costs egress and is never automatic (revalidate.automaticMediumClass stays Existence). Key missing (double red edge, a slashed-circle glyph) is an encrypted copy whose recorded key id cannot be resolved right now: ErrClassUnavailable, drawn as itself, never as a weaker class wearing a stronger name and never as a plain "Encrypted". Decrypt failed (solid red, a cross) is a decrypt-verify that ran and failed closed: wrong key, tampered chunk, truncated tail or reordered chunk, named in words beside it. Plaintext (dashed neutral, a hollow-box glyph for an open copy) is an unencrypted copy, drawn deliberately so that a local plaintext copy next to an encrypted off-site copy of the same artifact reads as two different things on one row.

Why the chip is not coloured text. As in #984: the ink is always the body text colour, the state lives in the glyph shape, the border style (solid, dashed, dotted, double) and the words, with colour as a redundant fourth cue. Every chip stays at body-text contrast in both themes and reads to someone who cannot tell the hues apart. --text-3 is used for no text in this note and --edge-3 for no text at all.

2. Settings: the Retained-copy encryption card, off and on

Decision. One card on the Settings page, directly after Storage destinations and before Workflow (the order the Workflow and Assurance cards already follow: the destination is declared, then what happens to a copy on its way there), in the same shape as the cards around it. In its default state the card is a single switch and a sentence that says what Off is: today's bytes, today's rows, today's timings, nothing changed (FR-59, the off is byte-identical invariant). There is no format, cipher, chunk-size, nonce or KDF field anywhere on the card, in either state. The draft's algorithm: auto is gone, not hidden behind "Advanced": its effect could not be stated from the code because the format is a property of the build and no operator input changes it, so by docs/epic-checklist.md §5 it gets no control and no pop-up. What the build does use is drawn once, as a deployment-wide readout with a lock (format id and version as the per-copy metadata records them), so the absence of a knob is visible and nobody later "fixes" it.

The enabled card is a status card first. It shows the active managed key by id, when it was created and its status; whether a recovery bundle has been confirmed and when; and, when it has not, the bundle warning from section 3 in the card itself. The actions are Export recovery bundle, Rotate key and Use an external key reference instead. There is no Show key, Copy key or Reveal action and no field that would hold one (FR-63). Every mutating control echoes its command through CommandEcho below it.

Smart defaults, chosen so the enable flow asks one question. Three options were weighed for what enabling should ask. (a) Ask nothing and mint a managed key: simplest, but an operator who already keeps keys in a secrets manager would have a managed key created against their policy before they could say so, and minting material without asking is a custody action taken silently. (b) Ask the full set (key source, format, rotation cadence): every one of those but the first is either unstatable from the code or not a property an operator should set. (c) Ask one question, who holds the key, with the managed key pre-selected. (c) is the one decision that changes a trust boundary, it leaves the format to the build, and it maps one-to-one onto the two shapes the config has (key_provider absent, or secretref-shaped). (c) is drawn in section 3.

3. Enabling: one question, then the bundle warning and its confirmation

Decision. Turning the switch on opens a dialog with one question: Who holds the key? A key this deployment manages is pre-selected and says plainly where it lives (a 0600 file in a 0700 directory in the state directory, under the same custody rule the other secrets already follow) and the one honest sentence about it: anyone who can read that file can read the copies, so the recovery bundle is what moves the key off this host. A key I keep elsewhere switches to the reference-only flow in section 7. The primary button is Enable and create key and the echo shows the two commands it is equivalent to.

The bundle warning appears the moment the key exists, where the operator is standing. After the key is created the card shows the No confirmed recovery bundle notice (a two-pixel warning edge, a diamond glyph). It is a durable health fact (migration 0015, FR-66), not a toast and not an alert: it is still there after a reload and after a restart, and only a human confirming a bundle clears it. The same fact is drawn on the Dashboard health card in section 10, because a settings card is a surface the operator has no reason to revisit. The notice does not block the switch: encryption is enabled and copies are being written. It blocks nothing and nags durably, which is the honest shape for "your copies are encrypted and you cannot yet recover them without this machine".

The one-time export is explicit, warned once, and not obstructive. Export recovery bundle opens one dialog that says what the bundle contains (the key material, integrity metadata, and the clean-machine instructions), that this is the only time the material leaves the deployment, and that the file is the thing to protect. One checkbox, I understand this file can decrypt every copy made under this key, enables Download bundle. The download is a file; nothing is rendered to the screen, there is no "show as text" alternative and no QR code, and the dialog closes on completion. That is the single exception to no key byte is rendered after generation, and it renders nothing either: the material goes into a file the operator chose to download.

Confirming is a separate, deliberate act. After the download the notice changes to Bundle exported, not yet confirmed and offers I have stored the bundle safely. Confirming writes the durable fact and clears the health state. Two options were considered and rejected: clearing the warning on download (the download may have landed in a browser folder on the same host, which moves nothing off it), and demanding the operator re-upload the bundle to prove they have it (which would make this UI accept key material, the one thing it must never do). The confirm is a statement by a human and is recorded as one, with its correlation id in the feed.

4. The per-set control: Inherit / Off / Required, beside the retention card

Decision. A card on the Backup Set detail page, directly under Retention in the right column, in the same segmented-control shape the Assurance card from #984 uses. Three values and only three: Inherit, Off, Required. Inherit shows the value it currently resolves to, exactly as the retention card attributes an inheriting set to the deployment's chain, so a global edit is visibly the thing that moved this set, and so inherit and an explicit off stay distinguishable on screen the way #989 keeps them distinguishable after Validate. Required shows what it means in one sentence: a copy to a destination is refused rather than written in plaintext, and the refusal happens before any source or medium deletion step (FR-66).

The written "no". Rotation cadence, format and chunk size are not properties of a backup set and get no per-set control, in the same way #984 refused per-set staging and concurrency. A per-set format would make one artifact's two copies unreadable by two different rules for nobody's benefit. The per-set surface is mode and key_provider, nothing else, and this card draws key_provider only as a read-only attribution (Key: the deployment's managed key) with the per-set override reachable through the same reference-only flow as section 7.

A kopia-engine set. A set whose engine is kopia already has its repository encrypted by kopia's own format under the repository passphrase. Its card draws the control disabled and a statement of fact in its place, with the wording owned by ADR 0027 (#989) and the docs (#997). This note decides only that the control is not drawn live for such a set, because a live Required there would promise a second cipher the epic explicitly does not ship.

5. Backups and Backup detail: per-destination and per-copy indicators

Decision. The Backups list gains one Encryption column of chips per row, one chip per copy, in destination order. The Backup detail Copies table gains an Encryption column between Access and Verification, carrying the section 1 chips, plus two rows in the artifact facts: Plaintext digest (which is artifacts.local_hash; the Artifact card's existing Checksum row keeps its label and gains the word plaintext only on an artifact that has an encrypted copy, so a deployment with encryption off sees no change) and, per encrypted copy, Stored-bytes digest with the format id, version and key id beside it. They are two numbers in two places and the labels say which is which, because two numbers that disagree about the same file are not a measurement (#662), and under encryption they are supposed to disagree.

The row this feature exists for. One artifact, a plaintext local copy and an encrypted off-site copy, is drawn as Plaintext beside Encrypted plus Verified recoverable 3d ago. The Verification column keeps saying what class was achieved (existence only, content), and Content verified over an encrypted copy is only ever written when the decrypt-verify matched the plaintext digest. The chip and the class never contradict each other because they come from the same row. The three Assurance claims at the top of Backup detail (ArtifactAssuranceCard) are untouched: Content verified over an encrypted copy can only come from the same decrypt-verify that writes Verified recoverable, so the claim chip and the encryption chip cannot disagree.

Key missing, where the operator already looks. A copy whose recorded key id cannot be resolved shows Key missing on the Backups list row and in the Copies table, and the destination block on the set page shows the same chip beside the destination name. It is also the one new alert.Kind (a required policy whose key cannot resolve), so it reaches the Dashboard health card and the feed. An operator meets it on four surfaces before Settings is one of them.

6. Key rotation, and the retirement that is refused

Decision. Rotate key opens a dialog that states the three facts rotation has and the one it does not: new copies use the new key from now on; every copy made so far stays readable through the key id recorded against it; the old key stays in the registry as Retired; nothing is re-encrypted (FR-65, and the cut list). The dialog warns that the new key has no confirmed bundle yet, so the section 3 notice comes back the moment rotation completes, and the echo shows the command. Rotation is a durable operation with a Result and appears in Active operations and the terminal like any other.

The key list is metadata only. Under the active key the card lists every key the registry holds: id, created, retired, status, and the count of ACTIVE placements that record it. There is no fingerprint, no first-eight-characters, no "verify this matches your bundle" string: a fingerprint of key material is a function of key material, and the probe reports whether a key resolves, never what it is.

Retire is refused, naming the copies. Retire on a key that any ACTIVE placement still records is a refusal, not a confirmation: the dialog names the copies (as many as fit, with a count and a link to the Backups list filtered to that key id), says that retiring would orphan them, and offers nothing else. The CLI line under it is the same refusal with a non-zero status. A key with zero copies recording it can be retired, and the dialog says so in the same shape.

7. The external key reference: a path, a variable name or a command, and never material

Decision. The advanced flow is one card with a three-way choice, File, Environment variable, Command, exactly the three sources secretref.Ref has, and one single-line text box whose label changes with the choice: Path to the key file, Variable name, Executable. The box is a reference. It has no multi-line form, no paste-the-key variant, no file-upload control, and no "or enter the key directly" link anywhere. The server refuses a value that is key material rather than a reference at Load (the fixture beside 53-invalid-inline-medium-secret.yaml), and the UI draws that refusal in the same words rather than pre-empting it with a guess about what material looks like (FR-64).

Test, with three answers. Test reference runs the resolvability probe and reports one of three states, each its own chip: Resolves (green, check), Declared but unreachable (double red edge, slashed circle, with the refusal vocabulary the resolver already has: no source, ambiguous, empty, too large, custody), and Not declared (neutral dashed). None of the three renders a byte of what was resolved, and the success state does not say how long the key is or what it starts with.

It reads back as its description. After saving, the card shows file: /etc/retnd/keys/offsite.key, or env: RETND_OFFSITE_KEY, or command: /usr/local/bin/fetch-key (the executable without its arguments), which is what secretref.Ref.String() renders and why the API field is write-only. The text box is not pre-filled from the readback: a reference you can parse back out of the UI is a second way to declare a key, which the type's missing UnmarshalJSON exists to prevent.

8. Verify recoverable: the operator-initiated decrypt-verify and its three endings

Decision. Verify recoverable sits in the Copies table on an encrypted copy and in the destination block of the set page. It opens a dialog that says what will happen in order (the key is resolved, the object is streamed and decrypted, the plaintext digest is compared to the recorded one, nothing is written to disk), shows the egress the read will cost in the words the provider gives (the same cost panel #984 draws for a thaw, since this is a Content-class check and Class.CostsEgress() is true for exactly that), and requires I accept this read before Verify now is enabled. Nothing in the product schedules this. The echo shows the command and its dry-run form.

The three endings are three chips. A match writes Verified recoverable with its age and verification_class: content. A key that cannot be resolved ends as Key missing before any byte is read and spends nothing. A decrypt that fails closed ends as Decrypt failed with the reason in words: wrong key, authentication failed at chunk N of M, truncated at N of M bytes, chunk out of order. No partial plaintext is written or shown on any of them, and the dialog says that, because the natural question after "failed at chunk 412" is "so where is what you got", and the answer is nowhere.

Progress is per copy, not per chunk. The operation reports bytes decrypted so far against the stored size through the existing app.Progress counters (nil outside the transform, a non-nil zero when it has started and read nothing). The feed gets one durable entry for the start and one for the result; chunk progress is live-only.

9. Live states: Encrypting and Decrypt-verifying in Active operations and the docked terminal

Decision. Two new stages join the existing progress vocabulary: Encrypting on the copy path (between the local commit and Uploading) and Decrypt-verifying on the verify path. Each is one line in the docked terminal with its byte counter, in the terminal's own inks, and one stage in the Active operations card. A stage line names the destination and the key id, never the key. The terminal's existing filter chips (Everything, Engine, per set) apply unchanged. A reload re-reads the durable operation and shows the same stage and the same byte count; it does not start a second transform.

A refusal is a line, not a stage. A required policy whose key cannot resolve refuses the copy before the first destructive step and the terminal shows the refusal in the danger ink with the set, the destination and the key id, followed by what was not done: the source was not deleted, the medium was not touched. The Active operations card for that run ends with Refused: key missing rather than an error glyph with no words.

10. Degraded states on the Dashboard and the set page, not only in Settings

Decision. The Dashboard gains one row per encryption condition that holds, inside the Backup health card (HealthSummary.tsx) and in the same banner vocabulary the Dashboard already uses for its warnings (Banner and WarningBanner, never dismissible for these two, for the reason Banner.tsx gives: the words are the only thing standing between an operator and a misunderstanding): No confirmed recovery bundle (warning edge, the diamond glyph, with how long it has held and a link to the Settings card) and A required key cannot be resolved (danger edge, the slashed circle, with the key id, the sets it affects and how many copies are being refused). The zero value of the new health.Report section reads "this deployment encrypts nothing" and draws no row at all, so a deployment with encryption off shows no change here, which is also how the test can tell the zero value is not doing the work.

The set page. A set under a required policy with an unresolvable key shows the refusing state in the destination block, next to the destination, with the same chip as the Backups list. The operator standing on the set page to find out why last night's copy did not go sees it there, and the Settings card is the fourth place they could learn it rather than the first.

12. Reviewed against Backup Manager.dc.html: what follows it and what deliberately does not

Follows the canvas and the build. Card shape, eyebrow headings, the segmented control, the primary, neutral and danger button weights, the Copies table on Backup detail (PlacementList.tsx: Where, Location, Copy size, Class, Access, Verification), the Active operations card, the docked terminal and its inks, and the token set, all unchanged. Where the canvas and ui/shared/src/design-system/tokens.css differ (the build moved --text-3 to a text ink at 4.5:1 and added --edge-3 for edges, #1235), this note takes the build's values, because the canvas predates both. Every chip is the same shape as the three Assurance claims from #984 (assurance.css), with new glyphs and words.

Diverges, and why. The canvas draws a green Verified tick and a Checksum passed validation line for a backup. This note adds no encryption state to either and lets none roll up into them: they are the producer-manifest checksum of the plaintext, and the build has since retired the green header tick (BackupDetailPage.tsx, EPIC Q). Encryption is drawn only as the two-chip pair in section 1. The canvas has no encryption vocabulary at all (the word occurs once, in unrelated copy), so the chips, the bundle notice and the external-reference card are additions in its shape rather than reinterpretations of anything it draws. The canvas's text boxes and segmented controls take --border-strong for their edge, which is 1.69:1 on the light surface; this note uses --edge-3 as the shipped assurance CSS does, so a control edge meets 3:1. The canvas draws the Settings page as one column of cards in the order of the build at the time; the new card goes where the build puts a destination-adjacent card today (after Storage destinations), not where the canvas would.

13. Drawn as absent

No KMS or Vault provider field (the command reference is how a secrets manager is reached). No re-encrypt-everything action on rotation. No automatic or scheduled decrypt-verify. No per-set format, chunk size or cadence. No key fingerprint, key preview, "show key" or QR. No field that accepts key material, including the bundle confirmation, which is a statement and not an upload. No encryption of object names: the destination block keeps showing the full key under the bucket and the docs say what that means. No second cipher for a kopia-engine set. No audit view beyond the activity feed. Where a number is not computable (a size before the first copy, an age before the first decrypt-verify), the row is missing rather than showing a placeholder.
